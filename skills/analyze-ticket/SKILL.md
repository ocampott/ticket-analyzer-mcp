You are handling a ticket-analysis request. Natural language is the primary interface; do not ask the user to restate the request as `/ticket-analyzer:analize`.

1. Read the package canonical [`../../AGENTS.md`](../../AGENTS.md) when that package-relative path is resolvable, and read the consuming repository's `AGENTS.md` only for local safety and project instructions. Do not treat the consumer file as package authority. If the package canonical workflow is unavailable, apply the standalone contract below: detect the provider, fetch the complete ticket, explore the relevant codebase, and produce a concise plan before changing anything.
2. Extract the provider and identifier from the request. Prefer an explicitly named provider; otherwise use Jira key format, numeric Azure DevOps ID, or Trello ID fallback. Ask only when the provider is genuinely ambiguous.
3. Fetch the ticket with the matching MCP tool and start with `include_images: false` and `include_text_attachments: false`. Read all ticket evidence that can affect the work, including comments, child items, checklists, refinement decisions, attachment inventory, and relevant attachment contents. For Azure, read all returned children and stop if the hierarchy is truncated until it can be fetched completely.
4. Use `analyze_ticket` for structured supporting evidence when helpful. Its deterministic, ticket-only hypotheses are not confirmed requirements, blockers, or estimates; interpret the MCP context yourself because it is not the final implementation plan.
5. Read `.claude/project-context.md` and `.claude/patterns.md` when present as navigation hints only, regardless of age. Re-read exact referenced source on every reuse, recording actual revision and dirty/unknown status. A pattern record requires its name, exact repo-relative paths and symbols, verified date/revision, applicability, and limits; never fabricate or append stale duplicates.
6. The complete necessary change is the goal: map every requested behavior and restriction to ticket/refinement evidence, exact current implementation, necessary delta, complete plan, and proportional verification. Include Backend, Infra, or other repositories when the ticket or inspected code proves they are needed; otherwise label repository-unverified inferences without turning them into requirements or blockers. Report in the project's established language convention (normally concise professional Rioplatense Spanish), keeping technical paths, identifiers, tool names, and commands exact.
7. Analysis is read-only. ### Standalone fallback contract

If the package canonical `AGENTS.md` cannot be resolved, apply this contract directly rather than relying on unrelated consumer-repository instructions:

- **Evidence and scope:** fetch and read all ticket evidence that can affect the work, including Azure children and relevant attachments; map every requested behavior and restriction to ticket/refinement evidence, exact consuming-repository source paths and symbols, current implementation, and the necessary delta. Classify each item as already exists, necessary delta, or unresolved, then give the complete necessary scope and proportional verification. Mark unavailable code or cross-repository work as `repository-unverified` rather than guessing.
- **Azure output:** return `## Análisis y estimación`, grouped only by `Frontend`, `Backend`, `QA`, and `Infra` areas with real work; include QA in every estimate, state assumptions, identify required work outside the current repository, and split `XL` work. Follow it with `## Detalle técnico`, using the same areas and exact paths or endpoints.
- **Jira/Trello output:** return `## Plan de implementación` with `Contexto`, numbered `Pasos`, `No toques`, `Verificación`, and `Talla`; every implementation step names an exact path or endpoint and cites the evidence-grounded necessary change.
- **Cache boundary:** analysis is read-only. Only explicit, bounded cache-only consent may authorize `.claude/project-context.md` and/or `.claude/patterns.md`, after verifying those paths are ignored; never write application files, migrations, comments, or `.gitignore`.
